# PaiAgent 二期改造：开发方向与架构规划

> 本文档是「动手开发前」的规划成果：源码核实 + 方向定位 + 目标架构 + 分阶段流程 + 准备工作。
> 生成日期：2026-10-15 ｜ 状态：待评审，尚未开始编码

---

## 一、结论速览

1. **不要重写平台，要补「运行时治理层」**。PaiAgent 的编排骨架（DAG/LangGraph/ReAct/Skills/节点执行器）已经完整，缺的是「可信执行边界 + 性能 + 可靠性」这一层。
2. **改进指南的评估基本准确**，但代码比指南基线更先进——条件分支、DAG 断点续跑、ReAct Agent、多模型配置、朴素混合检索都已存在。
3. **启航 ERP「完善版」是金矿**：它的 `cn.qihangerp.agent.*` 包已用同源技术栈（Java + Spring Boot + Spring AI + MyBatis-Plus）**完整实现了简历里声称的每一个模块，且带全套测试**。开发方向的核心是「移植适配」而非「从零发明」。
4. 四个必做模块，正好对应简历中 PaiAgent 的四个核心 claim：工具权限分级审计、持久化分层记忆、RAG 混合检索与离线评测、有界并行 DAG。

- PaiAgent 已有 `WorkflowEngine`/`GraphBuilder`/`AgentToolRegistry`，应「改造」而非「新增一套」平行引擎。

## 四、开发方向定位

**一句话**：把 PaiAgent 从「能跑通的编排平台」升级为「可审计、可恢复、可评测的企业 Agent 运行时」，落地四个可量化、可面试讲深的模块。

实施优先级（对齐「可信骨架优先」）：

| 优先级 | 模块 | 价值 | 难度 |
|--------|------|------|------|
| **P0-1** | 工具权限分级与审计（受限自治层） | 最有辨识度、面试核心 | 高 |
| **P0-2** | 持久化分层记忆 | 生产可靠性 | 低 |
| **P0-3** | RAG 混合检索 + 离线评测 | 可量化性能提升 | 中 |
| **P1-1** | 有界并行 DAG 调度 | 可量化性能提升 | 中 |
| **P1-2** | LangGraph 条件边 + Checkpoint 补齐 | 功能完整性 | 中 |
| P2（可选） | 通用 MCP、失败补偿重试、Skills 版本管理 | 工程深度 | — |

## 五、目标架构

在现有包结构上，**新增/扩展**以下层（全部挂在 `com.paiagent.engine` 下，不碰 Controller/Service 业务层）：

```
com.paiagent.engine
├── policy/          # AutonomyLevel、ToolPolicy、PolicyRegistry
├── gateway/         # ToolGateway(AOP)、IdempotencyGuard、ActionLedger 写入
├── scheduler/       # ParallelDAGScheduler、NodeResult、NodeStatus
├── memory/          # MemoryScope、MemoryRecord、持久化 AgentMemoryService
├── rag/             # BM25Retriever、HybridRetriever、Reranker、RagEvaluator
└── tenant/          # TenantContext(ThreadLocal)、TenantProjection
com.paiagent
├── entity/          # ActionLedger、ApprovalRecord、TenantConfig
├── mapper/          # 对应 Mapper + XML
└── controller/      # ApprovalController、LedgerController（查询审计/审批）
```

**执行链路（改造后）**：
```
Agent 节点 → ToolGateway(AOP) → 权限判定(AutonomyLevel) → 幂等守卫 → 租户投影
          → AgentTool.execute() → ActionLedger 异步落审计
          （ESCALATE/DRAFT 走 ApprovalQueue，人工确认后恢复）
```

## 六、关键技术选型决策

| 决策点 | 推荐方案 | 备选 | 理由 |
|--------|---------|------|------|
| **向量检索** | MySQL `FULLTEXT`（ngram parser）做 BM25 路 + 应用层内存向量索引（HNSW 简化版）做稠密路 | 换 PostgreSQL + pgvector | 保持 MySQL 现状，避免换库成本；10 万级数据内存索引足够 |
| **并行调度** | `CompletableFuture` + 有界 `ThreadPoolExecutor`（保留串行开关） | 自建调度图 | 复用现有拓扑排序结果，最小侵入 |
| **记忆存储** | MySQL `agent_memory` 表（扩展字段）+ Redis 会话缓存 | 纯 Redis | 表已存在，只需加 `session_id/user_id/importance/expires_at` 列 |
| **工具权限** | `@ToolPolicy` 注解 + Spring AOP 拦截（仿启航 ToolGateway） | MethodInterceptor 手工代理 | AOP 声明式、与 Spring AI 解耦 |
| **审批流** | 新增 `approval_record` 表 + `ApprovalController`（人工确认后 `resumeExecution` 恢复） | 消息队列 | 复用已有断点续跑机制 |

## 七、分阶段开发流程（写→验→报，每个迭代独立可交付）

> 每个迭代完成后跑 `mvnw test` + 对应性能基准，产出可量化指标（对应简历 §4.1）。

- **迭代 1 — 工具权限分级与审计（P0-1）**
  产出：`AutonomyLevel` 枚举、`@ToolPolicy` 注解、`ToolGateway` AOP、`ActionLedger` 表/实体/Service、`ApprovalController`；测试覆盖五级放行/拦截 + 跨租户校验。
- **迭代 2 — 持久化分层记忆（P0-2）**
  产出：扩展 `agent_memory` 表、`MemoryScope`(WORKING/SESSION/USER/TEAM)、重构 `AgentMemoryService` 接 MySQL+Redis、`SensitiveDataMasker` 脱敏、TTL 清理；测试覆盖跨会话召回 + 过期淘汰。
- **迭代 3 — RAG 混合检索与离线评测（P0-3）**
  产出：`BM25Retriever`(FULLTEXT)、`HybridRetriever`(RRF 融合)、`Reranker`、`RagEvaluator`(Recall@K/MRR)、100+ 条评测集；性能基准 1 万条 <50ms。
- **迭代 4 — 有界并行 DAG 调度（P1-1）**
  产出：`ParallelDAGScheduler`、`NodeResult`、失败传播 + 独立分支取消 + 指定节点续跑；串/并行双跑一致性测试。
- **迭代 5 — LangGraph 条件边 + Checkpoint 补齐（P1-2）**
  产出：`ConditionalRouter`、`GraphBuilder.addConditionalEdges`、`LoopNode`(maxIterations)、LangGraph 断点恢复。

## 九、已确认决策（2026-10-15 拍板）

1. **向量方案** → ✅ **维持 MySQL**：FULLTEXT(ngram) 做 BM25 路 + 应用层内存向量索引（HNSW 简化版）做稠密路，不引入 pgvector。
2. **落地范围** → ✅ **四~五模块全做**：工具权限、持久化记忆、RAG+评测、并行 DAG、LangGraph 条件边（迭代 1~5 全部落地）。
3. **ERP 工具对接** → ✅ **接入启航 ERP 真实 Tool**：将启航 `OrderTools`/`RefundTools`/`OrderActionTools` 等受控业务工具移植进 PaiAgent，做端到端「Agent → 工具网关 → 审计/审批」演示；移植只参考不改启航源码。

> 注：ERP 真实 Tool 对接受「启航仅参考权」约束，移植时重写适配 PaiAgent 的 `com.paiagent` 包结构与 Spring AI 1.0.0-M5 依赖；其数据库（ERP 业务表）可只读对接或本地另建演示数据源，实际方案在迭代 1 前单独确认。
